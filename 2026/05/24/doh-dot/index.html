DoH 与 DoT：加密 DNS 解析

一、为什么需要加密 DNS？

传统 DNS 使用 UDP/TCP 53 端口，查询和应答以明文传输：

这意味着：

  • 中间人（路由器、公共 WiFi、运营商）可以看到你访问了哪些域名
  • 攻击者可以篡改 DNS 应答，把你导向恶意 IP（即 DNS 劫持）
  • 隐私泄露：浏览记录可被监控、记录

DoH 和 DoT 都是给 DNS 查询「加 TLS 加密」的方案，让解析过程既保密又更难被篡改。

二、DoT 是什么？

DoT（DNS over TLS）= 在 TLS 加密通道 里传输 DNS 协议。

项目 说明
全称 DNS over TLS
标准 RFC 7858
端口 853（专用端口）
加密 TLS 1.2 / 1.3
协议形态 仍是标准 DNS 报文，只是外层包了 TLS

特点：

  • 端口固定为 853，网络管理员容易识别和管控
  • 与操作系统 DNS 栈集成较好（Android 9+、部分 Linux 发行版原生支持）
  • 适合在系统层面统一启用

三、DoH 是什么？

DoH（DNS over HTTPS）= 把 DNS 查询封装在 HTTPS 请求 里发送。

项目 说明
全称 DNS over HTTPS
标准 RFC 8484
端口 443（与普通 HTTPS 相同）
加密 TLS（走 HTTPS）
协议形态 DNS 报文编码为 HTTP GET/POST 请求

特点：

  • 流量混在普通 HTTPS 里，不易被单独识别和封锁
  • 浏览器（Firefox、Chrome、Edge）和应用层集成方便
  • 企业网络、防火墙更难按「DNS 流量」做策略分流

四、DoH vs DoT vs 传统 DNS

对比项 传统 DNS DoT DoH
端口 53 853 443
是否加密 否 是（TLS） 是（HTTPS/TLS）
隐私保护 弱 强 强
防劫持 弱 强 强
流量特征 明显 较明显（853 专用） 隐蔽（像普通网页）
典型部署层 系统 / 路由器 系统 / 路由器 浏览器 / 系统 / 应用
企业管控难度 低 中 高

提示

DNSSEC 补充
DoH 和 DoT 解决的是传输层安全（加密 + 防篡改），不等于 DNSSEC。若要校验应答是否被权威源签名，还需配合 DNSSEC。

6.4 浏览器级 DoH

Firefox：

Chrome / Edge：

设置 → 隐私和安全 → 安全 → 使用安全 DNS → 选择 Cloudflare / Google 或自定义。

警告

浏览器 DoH 的作用范围
浏览器 DoH 只保护浏览器内的 DNS 查询；系统其他程序仍走系统 DNS。若要全局生效，应在系统或路由器层配置。

6.5 路由器 / AdGuard Home

在 AdGuard Home 的上游 DNS 中勾选「DNS-over-HTTPS」或「DNS-over-TLS」，路由器 DNS 指向 AdGuard Home 后，全家设备统一走加密 DNS。

八、局限与注意事项

8.1 不能替代 HTTPS

DoH/DoT 只加密 DNS 查询，网站内容仍需 HTTPS 保护。两者配合使用才是完整方案。

8.2 无法隐藏「你连了哪个 IP」

加密 DNS 隐藏的是域名查询，但连接目标 IP 的 TLS 流量仍可能被 SNI 等手段分析（DoH 对此无额外帮助）。

8.3 企业环境可能冲突

公司内网依赖内网 DNS 解析内部域名（如 intranet.corp.local）。全局 DoH 可能导致内网域名无法解析，企业通常采用分流策略（内网走公司 DNS，外网走 DoH）。

8.4 信任转移

使用公共 DoH/DoT 意味着把「谁能看到我的 DNS 查询」从 ISP 转移给了 DoH 提供商。选服务商时关注其隐私政策。

8.5 与 DNS 劫持防护的关系

DoH/DoT 可显著降低链路上被篡改 DNS 应答的风险，是本机、路由器被劫持时的有效补救手段之一。详见 DNS劫持原理与防护 — 进阶防御。

九、速查清单

  • 了解传统 DNS 明文传输的风险
  • 选定可信 DoH/DoT 提供商（国内推荐阿里 / 腾讯）
  • 在系统或路由器层启用加密 DNS（而非仅浏览器）
  • 关闭回退到明文 DNS（AllowFallbackToUdp $false）
  • 用检测工具验证加密 DNS 已生效
  • 企业用户确认内网域名解析不受影响
