Web 拒绝服务（DoS）

2026-06-28 WEB渗透 ， 基础漏洞

一、是什么

Web 拒绝服务的本质：服务端有一段”资源生成”逻辑，其中的参数被客户端控制，且没有对生成资源的规模做限制。攻击者把参数放大到极端值后，服务器 CPU / 内存 / 磁盘被吃满，拒绝正常请求。

和传统网络层 DDoS 不一样——不需要成千上万的肉鸡，一个 HTTP 请求就能把服务器打趴。

常见触发的点：

  • 图片生成接口的参数可控（验证码、头像裁剪等）
  • 文件上传接口无次数/大小限制
  • 压缩包上传后自动解压，内容远超预期
  • JSON/XML 解析时的递归展开（Billion Laughs 攻击）

二、验证码拒绝服务（Captcha DoS）

这是最常见的 Web DoS 类型。开发者为了让验证码在不同设备上显示正常，会接受尺寸参数——但往往没有上限校验。

2.1 漏洞代码

不只是前端 HTML 属性被放大——很多验证码接口是服务端实时渲染生成的（GD 库、ImageMagick），服务器要根据 width/height 在内存里画图。9999×9999 意味着分配几百 MB 内存去处理，一堆请求同时来，服务器直接 OOM。

2.2 测试方法

  1. 打开登录页，找到图片验证码的请求
  2. Burp 抓取验证码请求包
  3. 在 URL 参数中尝试拼接隐藏参数：height、width、size、margin、h、w
  4. 逐步增大数值，观察响应差异：h=111 → h=222 → h=9999

增大参数后看两个指标：

  • 响应时间：Burp 右下角的耗时是否明显变长
  • 响应字节：返回图片的大小是否随参数变大

也可以在 Burp 的 Render 模块直接看渲染效果——图片被拉长、拉扁、整体变大，就说明参数生效了：

三、压缩包解压炸弹（Zip Bomb）

上传功能支持 .zip 且自动解压——攻击者构造一个解压后体积远超压缩体积的炸弹文件。

压缩包里再套压缩包，层层嵌套。几个 KB 的 zip 解压后膨胀到几十 GB。

4.2 图片大小有限制

单个文件限制 300KB 又怎样——积少成多，发几千个一样塞满磁盘。限制单文件大小挡不住频率型 DoS。

五、防御

攻击类型 措施
验证码 DoS 限制 width/height 最大值（如不超过 500）；拒绝超范围的参数值
Zip Bomb 限制解压总大小、解压层数（最多 2 层）、解压文件数；不上传后自动解压
文件上传 DoS 限制单 IP 上传频率和总次数；设置磁盘配额
通用 凡是资源消耗由客户端参数决定的逻辑，全加上上限校验
应急 服务停止/重启；攻击者浏览器端关闭卡死的页面释放连接

一句话：只要服务端有一段逻辑的资源消耗由客户端参数决定、且没有上限——它就是一个潜在 DoS 点。验证码的 h/w 是最常见的入口，但不是唯一的。
