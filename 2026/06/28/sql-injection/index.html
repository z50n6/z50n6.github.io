一、SQL 注入原理

1.1 是什么

SQL 注入（SQL Injection）——攻击者通过用户可控参数中注入 SQL 语法，破坏原有 SQL 结构，达到程序意料之外的结果。

两个根因叠加：

  1. 程序员使用字符串拼接构造 SQL 语句
  2. 未对用户可控参数做充分过滤

四个字：拼接 + 未过滤

1.2 危害

增删改查数据库数据（脱库）→ 读写服务器文件 → 提权 → WebShell → 服务器权限。

1.3 分类

两大基本类型 五大基本手法 提交参数方式 注入点位置
数字型
字符型		 联合查询 → 报错注入 → 布尔盲注 → 延时注入 → 堆叠查询 GET / POST / Cookie / HTTP头部 URL / 搜索框 / 留言板 / 登录框

从上到下注入成本递增——联合查询最简单，堆叠查询最复杂。

四、报错注入

适用：数据库 SQL 语句的报错信息会回显在页面中。

基本思路：想办法让数据库在执行查询时报错，并且把我们要查的数据”夹带”在报错信息里。
concat 是把多个字符串拼成一条，0x5e 是十六进制的 ~ 符号，只是用来分隔方便看。
直接套公式，把里面 select database() 那部分换成你的查询。

4.1 group by（floor 报错）

原理：利用 count(*) + group by + floor(rand()*2) 的组合。floor(rand()*2) 随机输出 0 或 1，group by 对随机值做分组时会触发 MySQL 的 Duplicate entry 错误。报错信息恰好会把 concat 拼进去的内容显示出来。

4.2 extractvalue

原理：extractvalue(1, xpath) 是 MySQL 用来从 XML 中提取值的函数，第二个参数应该是合法的 XPath 表达式。我们传入 concat(0x5e,(select database()),0x5e) 作为 XPath——它不是合法的 XPath，于是 MySQL 报错：”XPATH syntax error: ‘数据库名‘“，数据库名就暴露了。

4.3 updatexml

原理：与 extractvalue 类似，updatexml(1, xpath, 1) 也是处理 XML 的函数，第二个参数必须是合法 XPath。我们传入非法 XPath，MySQL 报错带出数据。

五、布尔盲注

适用：页面有布尔类型的状态（正常/不正常），无回显、无报错。

核心思路：虽然看不到数据内容，但页面会呈现两种状态——正常显示 vs 页面异常。这就够了。通过构造 true/false 的条件，”一个问题一个问题”地问数据库，从页面状态得到答案。

打个比方：你看不到密码本，但每次你问”密码第一位是 a 吗？”对方会点头或摇头。问完 8 位就拿到了完整密码。这就是布尔盲注。

核心函数：

函数 作用 示例
length(str) 返回字符串长度 length(database())=8 → 库名 8 位
substr(str,pos,len) 从 pos 开始截取 len 个字符 substr(database(),1,1) → 第 1 个字符
ascii(str) 返回第一个字符的 ASCII 码 ascii('s')=115
if(expr,a,b) expr 真→返回 a，假→返回 b if(1=2,1,2)→2

六、延时注入

适用：怎么试页面都一个样——无回显、无报错、连布尔状态差异都没有。利用 sleep() 让数据库”卡顿”几秒，以时间差作为判断条件。

核心思路：把 if 条件判断和 sleep 组合——条件成立就睡 5 秒，条件不成立就正常返回。你自己掐秒表看页面加载时间就知道答案了。

核心函数：

函数 作用
sleep(N) 让数据库暂停 N 秒
if(expr, a, b) 如果 expr 为真，返回 a；否则返回 b
substr(str,pos,len) 截取字符串
length(str) 字符串长度

示例：if(database()='security', sleep(5), 1) — 如果数据库名是 security → 卡 5 秒，否则直接返回 1。

8.3 GBK 编码原理

GBK 也叫双字节编码——每个汉字用两个字节表示。它的编码范围是 [8140, FEFE]（第一字节 [81, FE]，第二字节 [40, FE]）。

举个例子，查「国」字的 GBK 编码：

「国」= B9 FA，B9 是高位字节，FA 是低位字节。

关键的坑在这里——反斜杠 \ 的 ASCII 码是 0x5C，而 5C 恰好落在 GBK 低位字节的范围 [40, FE] 内。这意味着：在 \（5C）前面放一个 [81, FE] 范围的字节，GBK 会把它俩当成一个完整的汉字来解码，\ 就被”吃掉”了，转义失效。

十一、MySQL 读写注入

11.1 三个前提

条件一：用户有文件读写权限

条件二：知道目标文件绝对路径（/var/www/html/、c:/phpstudy/www/）

条件三：secure_file_priv 不限制

值 含义
空 不限制
c:/a/ 限制在指定目录
NULL 完全禁止

注意：secure_file_priv 这个参数不能通过 SQL 语句修改。如果值是 NULL 或限制在某个目录，只能在 MySQL 安装目录下的 my.ini 配置文件中 [mysqld] 段加入 secure_file_priv=，然后重启 MySQL 服务才能生效。仅靠 SET GLOBAL 改不了它。

11.2 读取文件

有了 load_file()，SQL 注入不仅能偷数据——还能读服务器上的任意文件，等于”目录遍历”。

11.3 写入文件 → WebShell

into outfile 是 MySQL 语法，将查询结果写入服务器文件。写入 .php + Web 可访问目录 = WebShell。

into outfile 不能覆盖已有文件。必须写到 Web 根目录下才能用蚁剑连接——仅写入成功不等于可用。

Linux 注意：Linux 系统下 MySQL 默认以 mysql 用户运行，对 Web 目录通常没有写入权限，into outfile 往往写不进去。Windows + phpStudy 这类集成环境权限较高，写入成功率大很多。

十四、SQL 注入防御

14.1 采用预编译技术

参数化查询是预防 SQL 注入最有效的方法。数据库服务器不会将参数内容视为 SQL 语句的一部分，而是在完成编译之后再套用参数运行。

14.2 过滤输入内容，校验字符串

在数据提交到数据库之前，剔除用户输入中的不合法字符。如果值属于特定类型或有具体格式，拼接 SQL 之前就要校验其有效性。比如对于确定是整型的值，浏览器端和服务器端都需要验证是否为整型。

14.3 不要使用拼接的方式

避免将用户的输入数据直接放入 SQL 语句中，使用预处理语句和参数化查询，这样更安全。

14.4 限制数据库权限

权限最小原则。否则就有 GetShell 的风险。

14.5 避免直接向用户显示数据库错误

攻击者可以通过错误消息来获取数据库的信息。生产环境 display_errors=Off。

14.6 部署 WAF 等安全设备

归根到底，需要良好的编码规范，并充分利用参数化查询、字符串处理和参数校验等多种办法来保护数据库和程序的安全。

无效防御（别用）： addslashes()、黑名单关键字过滤、仅前端校验。
