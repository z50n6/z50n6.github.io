SSRF 和 URL 跳转的误区及测试插件介绍

2026-06-14 渗透测试 ， 漏洞挖掘

SSRF 和 URL 跳转的区别

用大白话来讲（不看官方定义，按我的理解写）：

  • SSRF（服务端请求伪造）： 攻击者通过前端的输入点，让服务器主动向该服务器内网或其他网站发起了一个请求。
  • URL 跳转： 攻击者往 URL 参数里写入一个恶意链接，然后发给受害者，受害者打开后页面直接跳转到攻击者准备好的钓鱼网站。

一句话区分：SSRF 是服务器在”偷偷”发请求，URL 跳转是浏览器在”明着”跳页面。

经常会陷入的误区

为什么容易搞混？

因为在测试 URL 跳转漏洞时，需要把存在 URL 的地方替换成其他网站。有时候替换后页面并没有跳转，但浏览器本地却向外发出了一次请求（比如页面里有 img 标签加载了远程资源、或者 JS 触发了本地请求等）。

这时候用外带平台（dnslog / Collaborator）一测，发现收到了请求，就误以为这是 SSRF 产生的，但实际上是浏览器本地发出的。

核心教训：收到外带请求 ≠ 一定是 SSRF，要先确认请求来源是服务器还是你本地。

实战中如何区分 URL 跳转和 SSRF

最简单的方法：

1. URL 跳转 → 网页会直接跳转到另一个网站

一般习惯用 www.baidu.com 来测试，但有些网站把 baidu.com 加了白名单，只能跳百度，其他域名不让跳。所以建议多备几个测试域名，比如 www.4399.com 来交叉验证。

2. SSRF → 网页不会跳转

  • 可回显的 SSRF： 目标 URL 的内容会在当前页面中加载显示出来（比如页面渲染了请求结果）。

  • 盲 SSRF： 完全没有任何肉眼可见的反应，只能靠外带平台来验证。

利用 Burp Collaborator 进行验证

Collaborator 是什么？

说白了就和 dnslog、ceye 差不多，它是 Burp Suite 自带的外带平台。外带平台通常会收到两种请求：

请求类型 说明
DNS 目标对域名做了解析查询
HTTP 目标主动向平台发起了 HTTP 请求

拿到 HTTP 请求的来源 IP 后，结合 ip138.com 等 IP 查询工具，就能判断这个请求到底是本地浏览器发的还是目标服务器发的，从而准确区分 URL 跳转和 SSRF。

自建外带平台：HiDnsLog

HiDnsLog 是 B站 UP主「犀利的远哥」用 Go 写的一款自建 DNSLog 工具，部署简单，支持 DNS 和 HTTP 两种外带方式。

为什么要用自己的 DNSLog？ 三个场景，公开平台搞不定：

  1. 厂商黑名单：dnslog.cn、eyes.sh 这些常用域名的根域已经进了大部分厂商的 WAF 黑名单，请求到 DNSLog 服务器的流量直接被拦。SSRF 明明存在，但你的外带收不到回显，等于白测。

  2. SRC 内网靶机需要绕过：有些厂商 SRC 提供了内网 SSRF 靶机域名，目标的访问路径不是直连的，而是先经过目标服务器再 302 跳转到内网地址。公开 DNSLog 处理不了这种跳转链路，自己的平台可以在跳转路径上加一层适配。

  3. 域名重绑定绕过：后台逻辑可能先检查你填的域名解析结果是不是内网 IP，是就拒绝。这时候需要把域名的 A 记录或 CNAME 记录做重绑定——先解析到一个合法公网 IP 过检查，过几秒再切到内网 IP，公开平台没这个灵活性。自己搭的 DNS 服务器可以精确控制解析策略。
