一、信息收集

拿到登录框后不要急着测漏洞，先把信息摸清楚。

1.1 识别框架/指纹

寻找 CMS、网页框架、厂商服务的特征指纹。确定框架后可以直接去 fofa 找同类型站，也可以针对性利用已知漏洞。

常见框架漏洞入口：

  • 致远A8任意文件写入+getshell（CNVD-2019-19299） - 广阔的编程世界 - 博客园
  • Thinkphp RCE POC 收集
  • Struts2 扫描
  • Weblogic 扫描
  • OA 漏洞
  • Nday

确认框架后针对已知漏洞打。常见指纹 → 漏洞映射：

框架/服务 常见漏洞
若依（验证码 +-×% 算术题） 任意文件下载、计划任务命令执行、XSS、多处 SQL 注入
Shiro（Cookie 中有 rememberMe=deleteMe） 反序列化 RCE
ThinkPHP 多版本 RCE
Struts2 多版本 RCE
Weblogic 反序列化、SSRF
各类 OA（致远、泛微、通达） 文件上传、未授权访问

Shiro 利用工具： ShiroAttack2

Struts2 检测利用工具： Struts2VulsScanTools

Nacos 利用工具： NacosExploit

1.2 JS 文件分析

JS 文件里经常藏着接口路径、敏感参数、测试账号等信息。

  • Chrome 插件：FindSomething、SnowEyes、StiffEyes
  • JSFinder
  • 多次爆破，遍历访问多级域名的 JS 文件

案例：使用 Nmap 对批量网段探测获得一个登录站，遍历目录获得 test 页面，在 test 页面的 JS 文件中获取到一个接口，通过该接口重置了主登录页面的密码。

地图 API Key 泄露：

登录页、注册页常嵌入地图组件，JS 中可能硬编码腾讯/百度地图 API Key。若未限制 Referer 白名单，可被盗用。

  • 搜索关键词：key=、sk=、TMap、BMap、qq.maps、api.map.baidu
  • 拿到 Key 后在本地页面引用测试是否限制 Referer
  • 参考：地图API劫持漏洞、地图API漏洞导致某行业用户信息泄露

1.3 目录扫描

  • dirsearch
  • 御剑
  • 多次爆破，遍历访问多级域名的目录

1.4 查看页面源代码

Ctrl + U 查看源代码，可能泄露：测试账号、后台结构、JS 接口、源码仓库地址等。

1.5 禁用 JS 测试

禁用 JS 后可能有意外收获。例如：登录失败时前端重定向回登录页，禁用 JS 后可停留在后台页面获得一定权限。某些权限校验依赖前端 JS 的，禁用后可绕过。

1.6 Sourcemap 文件泄露

前端项目（Vue/React/Angular）打包时若开启了 Sourcemap（.js.map）且未限制访问，攻击者可直接获取未压缩的源代码，从中提取路由、API 接口、密钥、业务逻辑等敏感信息。

常见路径：/js/app.xxx.js.map、/static/js/xxx.js.map，FindSomething、JSFinder 也可发现 .map 文件。

参考：记一次某医院Webpack源码泄露

二、认证安全测试

2.1 用户名枚举

利用页面回显差异判断用户名是否存在。

  • 用户名不存在 → 回显 “用户名不存在”
  • 密码错误 → 回显 “密码错误”

通过回显差异即可枚举有效账户。

修复方式：统一回显 “用户名或密码错误”。常规用户名无效时，可使用社工字典。

2.3 暴力破解（无验证码时）

无验证码或验证码可绕过时，直接爆破。

图形验证码绕过条件：

  • 验证码有时效但过长
  • 验证码前端校验
  • 验证码为空可绕过
  • 删除验证码参数可绕过
  • 万能验证码（0000、9999）
  • 图形验证码识别（见第五节）

JS 前端加密：

  • MD5、Base64
  • AES、DES、RSA → 找 key → BurpCrypto 插件

2.4 密码明文传输

抓包检查用户名密码是否明文传输，若是 HTTPS 内的明文一般可接受，HTTP 明文传输则为直接风险。

2.5 Session 会话固定

如果登录前后的 Session ID（Cookie 值）没有变化，则存在会话固定漏洞。攻击者可先获取一个未登录的 Session ID，将其植入受害者浏览器（如通过 URL 参数或 XSS），受害者使用该 Session 登录后，攻击者即可利用同一个 Session ID 冒充受害者。

参考：Session 会话固定漏洞详解

四、短信/邮箱接口安全

4.1 短信轰炸 / 邮箱轰炸

一般在发送验证码后抓包，不断 Repeater 即可。以下为常见绕过手法：

  • 添加空格或换行绕过

    空格或 \n、\r、\r\n 可叠加：mobile=XXXXXX\n\n

  • 参数污染绕过

    后台取数字部分发送短信，混入其他字符绕过已发送号码的校验：

  • +86 或 086 前缀绕过

  • 变量污染绕过（多参数同名）

    后台校验第一个参数，但实际传递以最后一个为准：

  • 数据长度绕过

    手机号定义为 11 位，但后台未校验长度，123 = 0123 = 00123，通过补零绕过。

  • 修改变量参数/接口类型绕过

    terminal=01 调用注册短信，02 调用密码重置短信，03 调用注册成功短信……修改参数值即可触发不同类型短信。

    1=注册，2=注册成功，3=密码重置 → 爆破 apitype 参数达到多类型轰炸。

    前端带入状态标识的：mobile=188&checkFlag=False → 改为 mobile=188&checkFlag=True 绕过。

  • 修改响应包绕过

    发送成功返回值 success，失败返回值 error。达到次数限制后修改返回值为 success 绕过。

  • 修改 IP 绕过

    限制当前 IP 频率的，更换 IP 或使用代理绕过。

  • 大小写绕过（邮箱专用）

  • 删除/修改 Cookie 绕过

    抓包删除或修改 Cookie 信息（全部删掉或删中间一部分）→ 空数值发包多次。

五、验证码安全

5.1 图形验证码

  • 验证码不会自动刷新（可复用）：输入一次验证码即可开始暴力破解

  • 验证码有时效但过长：纯数字或短字符且有效期长 → 可爆破

  • 验证码前端校验：前端 JS 判断验证码正确性 → 抓包绕过

  • 验证码回显前端：抓包就能在返回包里看到验证码

  • 验证码为空可绕过：不传验证码参数或传空值

  • 删除验证码参数可绕过：直接去掉验证码相关字段

  • 万能验证码：0000、9999 等开发测试用的万能码

  • 验证码可修改接收者：将 A 账号的验证码接收者改为 B，A 的验证码发到 B 的手机上

  • 图片验证码拒绝服务漏洞（验证码 DoS）

    漏洞原理：开发者为了让验证码适应不同显示大小，加入了隐藏参数（height、width、size、margin、h、w 等）。攻击者猜测出参数后，可以无限放大验证码图片尺寸，导致服务端生成超大图片消耗大量资源，最终拒绝服务。

    测试方法：

    1. 点击图片验证码，抓包
    2. 在请求参数中尝试拼接隐藏参数：height、width、size、margin、h、w（实战中 h、w、height、width 居多）
    3. 逐步增大数值观察响应：height=111 → height=222 → height=9999，看 Burp 响应时间是否明显延迟，或在 Render 模块中图片是否变形/放大

抓取验证码的数据包

修改参数值，观察响应字节差异。

也可以直接观察Render，看图片渲染是否发成变化。

看着这中验证码图片被拉长或者拉扁或者变大的情况就存在dos漏洞。

通过 bp插件-CaptchaDos来快速验证

5.3 短信验证码爆破

短信验证码通常为 4-6 位数字，有效期较长时可抓包爆破。

六、业务逻辑漏洞

6.1 登录绕过

修改响应包绕过：

  • 登录失败返回 {"success":false} → 改为 {"success":true} → 成功登录
  • 登录失败返回 {"status":0} → 改为 {"status":1} → 成功登录
  • 登录失败返回 0|sjhdfao → 查找 JS 发现判断值为 1 时登录成功 → 修改返回值为 1|sjhdfao

手机号与短信验证码未绑定：

自己的手机号获取到的验证码对所有手机号有效，直接用该验证码登录任意手机号。

注意：判定漏洞存在的关键

有时候两个手机号虽然收到了相同的短信验证码，但登录时系统会提示”验证码已使用”导致登录失败。这种情况下不存在漏洞。

只有拿到验证码后能成功登录到网站内部才算漏洞存在。不能仅凭两个号收到相同验证码就判定为漏洞，必须以能否完成登录为准。

6.2 任意密码重置

  • 随意输入验证码 → 发包 → 修改返回包 {"status":0} 为 {"status":1} → 成功重置
  • 验证码为 4 位 → 抓包爆破验证码
  • 参考案例：wooyun-2013-039809

6.3 任意用户注册

  • 爆破注册页面的验证码 → 任意用户注册
  • 通过邮箱验证构造验证链接：先正常流程发验证链接到邮箱，分析链接格式（可能由注册信息直接构成）→ 再次注册新账户，直接构造验证链接访问即可验证通过
